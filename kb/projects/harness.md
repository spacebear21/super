# harness

The workhorse image, its entrypoint, the dashboard, super-watch, super-sync and the seeds of this agent's own instructions. The hub is the bare repo ~/repos/harness.git, worktrees ~/repos/harness-<slug>; docs/runbook.md in the repo explains how everything is wired and why, so nothing of that is repeated here.

## Decisions taken out of band

- **Scheduled tasks live in this repo** (human, 2026-11-05). A committed schedule of every cron task, with the repositories each needs, so the schedule is in history and comes back whole on another machine, and the image pulls those repositories in. The payjoin audit's own install script and image notes were the thing this replaces: a crontab installed by hand is lost on every rebuild and nothing in the harness knew the task existed.
- **A deleted inbox note is a handled note** (human, 2026-11-05). super-watch drops queued note events whose file is gone before it prompts. The alternative, waiting until a note's modification time has been stable before announcing it, was rejected: the human is "not a fan of the delay". A rewritten note that still exists keeps counting as new.
- **Wake the super agent only for notes and dialogs, never for a worker finishing a turn**, because every wake-up costs a turn of context and most turn ends need nothing; when the super agent wants an answer it waits for it itself. Settled before my memory starts; the runbook carries the reasoning.
- **The super agent sits alone in its own workspace** and belongs to no project; harness work goes in its own workspace like any project.
- **A reviewed fix the human asked for may be landed in hub main and swapped into the root filesystem by hand** (done for super-watch) without waiting for an image deploy; the deploy carries it permanently. The root filesystem is wiped on rebuild, so the hub copy is the one that matters.

## Learned

- Claude Code holds text typed into a pane mid-turn until the turn ends, so a watcher prompt can arrive after the thing it announces is gone. Any mechanism that types into the super pane has to assume its message may be stale by the time it is read.
- A second super-watch with SUPER_DIR pointed elsewhere treats the real super pane as a worker, and the two watchers loop through each other's wake-ups. Test watchers need their own super agent or none.
- The dashboard worker's scratch agents and notes (names starting scratch-super-check) are test fixtures; answering one's dialog skewed its test.
- Right after `herdr pane run`, a process search for the command matches a short-lived wrapper first; the real process is the one that is still there ten seconds later. Watchers keyed on the wrong pid fire at once.
- A worker that touches its hand-off note up seconds after writing it makes a second event; the fix above makes that harmless, but a note that is deleted and rewritten before the prompt goes out is still named twice in one line.
- A long prompt (about 900 words) typed into a fresh OpenCode pane through Herdr can land in an empty input line and never submit, while the same prompt into the tab's root pane works. Writing the brief to a file and prompting with one short line that points at it works every time. Also: four same-direction splits in one tab make OpenCode panes too narrow to read; split alternately or use tabs.
- Agents sharing one output directory will delete each other's files: a fast OpenCode model, re-reading its brief after a second prompt, saw reports it had not written, decided it must have created them by mistake, and removed them under the global rule to make no unrelated changes. When several agents write to one place, say in each brief that other files there belong to other agents and must never be touched, or give each agent its own directory and merge afterwards. Snapshot shared outputs as they land.
- **Wake-ups wait while the human is typing** (2026-11-05): super-watch read the super pane's detection snapshot before prompting and holds its events while anything but the bare prompt character sits in the input box, because a wake-up typed into a half written message spliced the two together. Conservative by design: no box on screen or a failed read also holds. If wake-ups stop while nobody types, a Claude Code update probably changed the input box drawing.
- **Secrets reach agent-run loops through the environment, never a command line** (2026-11-05): a value in argv is readable by every uid through ps, while the environment is readable by that uid and root, which is the intended boundary. The super-sync loop was the one offender; the other secrets already went through a root-owned profile file. The live loop was restarted by hand the new way (logs to ~/.local/state/super-sync.log until the next deploy replaces it).
- **Wake-ups go through the session's inbox socket, typing is the fallback** (human, 2026-11-05: "could super watch not prompt outside of the main user prompt?"). Claude Code's cross-session messaging delivers a line as a peer message and never touches the input box. Two consequences settled with it: a SessionStart hook in the super agent's own settings writes the socket path and token to a private state file (the values reach hooks and Bash, not the claude process); and the box-wide managed settings accept unattested cross-session messages, because a project level accept is ignored when looser than managed settings and a script cannot attest its permission mode. That widens nothing in practice: the agent uid could already type into any pane through Herdr. The per-session flag alternative was rejected because Herdr's restore after a deploy resumes sessions without flags. Channels (an MCP server emitting events) were the other documented push and were passed over: research preview, development flag with an interactive dialog.
- Verified 2026-11-05 20:07: the first wake-up through the socket arrived as a peer message, input box untouched.
- Lesson: old /tmp/cc-socks/<pid>.sock files of ended sessions linger; a connect to one fails and the watcher falls back to typing.

- **A pasted brief can sit unsubmitted in a worker's input box for hours** (2026-11-06: the scheduler worker's brief from 16:43 was still a pasted block at 00:58, the agent idle with no completion). `herdr agent prompt` reports submission, not a started turn. After every brief, confirm the agent is working (`herdr agent get`), and treat an idle worker with no completion count as a stalled prompt, not a finished one.
- **OpenCode research agents on Token Factory are slow per turn, not per token.** kimi-k3.1-pro answers an agentic turn in one to three minutes (seven on long contexts), so a brief covering five web-research topics becomes an hour of wall clock: on 2026-11-06 the prior-art agent split its five named topics into five subagents of its own, each 15 to 30 serial tool turns, which was the right reading of the brief; the breadth was super's choice. The usage board barely moves meanwhile, since each turn adds a few thousand fresh tokens on top of cache reads. The human wants agents to keep their agency (2026-11-06: do not tell them not to spawn subagents). What to do instead: decide the breadth knowingly, state the deliverable and a time budget in the brief, split topics into separate runs when wall clock matters, and set a deadline after which super writes from its own knowledge.
- **`opencode run --dir` on a huge directory never starts.** Pointed at ~/.cache/payjoin-audit/repos (374 clones, 46 GB) it sat at init for an hour with no model call, no error, no output. Run OpenCode from a small directory (the scratchpad) and hand it absolute paths into the large tree.
- **Token Factory slowness is per model, server side.** Probed 2026-11-06 19:10 UTC while eight research calls were in flight: an eight-token answer took 72 s on kimi-k3.1-pro and half a second on glm-5.3 and deepseek-v4.1-flash; a 48k-token prompt to kimi took 31 s. No 429, no rate-limit or retry-after headers, no retries in the OpenCode log, machine load 0.2 on four cores. So a stalled usage board means the kimi queue, not a limit on us. When wall clock matters more than the last bit of quality, glm-5.3 is the strong model to use; the audit's measured speeds (speed_s in config.json) are the same phenomenon.
